# 选手平台与交互方案 v0.1

日期：2026-11-19。方案已由用户确认，首版已按本方案实施。当前功能、限制与启动步骤以 [WEB_PLATFORM.md](WEB_PLATFORM.md) 为准；本文保留产品设计，后续多环境与多节点条目不表示已经实现。

## 1. 已确认的方向

| 项目 | 已确认的选择 |
| --- | --- |
| 部署方式 | 一个局域网平台，多个选手通过浏览器上传，服务器统一运行 MuJoCo |
| 提交方式 | 使用平台模板打包 ZIP，包含代码、配置和离线模型权重 |
| 比赛组织 | 选手自行发起练习；管理员安排正式比赛 |
| 注册方式 | 邀请码注册账号 |
| 运行环境 | 平台统一提供运行环境和依赖版本，额外依赖由管理员处理 |
| 信息公开 | 正式成绩与正式回放对平台内已登录选手开放；代码、权重、练习记录仅本人和管理员可见 |
| 控制任务 | 选手同时负责视觉理解、寻找目标和 29 个关节的运动控制 |

局域网访问不等于代码可信。第一版可多人上传，默认只同时运行一局仿真，其余排队；以后再增加执行节点。当前仿真速度低于实时，界面分别显示仿真时间与实际等待时间，不承诺实时运行或未经测量的预计完成时间。

## 2. 选手的完整流程

1. 管理员生成有有效期、使用次数限制的邀请码，选手注册并登录。
2. 在“接口与环境”页下载模板，查看机器人接口、关节顺序、公开任务规则、统一环境和已发布的资源限额。
3. 在本地开发策略，将代码和模型按模板压缩。离线推理；运行时不临时下载权重或安装依赖。
4. 在“提交策略”页上传 ZIP，填写策略名称和可选说明。服务端保存不可覆盖的提交版本、文件摘要和环境版本。
5. 先做静态检查，再排队做隔离运行检查。失败时说明问题位置、实际值、要求和修改方法。
6. 接口检查通过后，自行发起练习；页面显示队列位置、准备状态、仿真进度和取消入口。
7. 完成后查看得分、任务事件、生命值变化、倒地复位、交通碰撞、错误日志和回放。练习记录保持私有。
8. 选择一个通过检查的版本报名正式比赛。管理员安排对手、场次和比赛配置。报名锁定后，新上传的版本不替换该场报名版本。
9. 正式比赛完成并由管理员发布后，平台内选手可查看正式成绩和回放；源代码与模型继续保密。

上传进度、检查进度、排队状态、比赛进度分开呈现，不能上传完成就提示“可以参赛”。接口通过也不代表机器人已经能站立、行走或完成任务。

## 3. 页面结构

| 页面 | 主要内容与操作 |
| --- | --- |
| 注册 / 登录 | 邀请码、账号、密码；邀请码无效、过期、已用尽的明确提示 |
| 提交策略 | 上传说明、ZIP 选择、策略名称、文件传输进度、版本列表、检查报告 |
| 练习与结果 | 发起练习、选择自己的已检查版本、查看队列、取消自己的排队或练习、结果与私有回放 |
| 正式比赛 | 报名版本、锁定状态、管理员排定的对手及时间、正式赛状态 |
| 排行与回放 | 已发布的正式成绩、场次、回放、公开计分事件；不显示私有运行日志 |
| 接口与环境 | 模板、输入输出说明、关节表、依赖及版本、资源限制、常见错误、申请额外依赖 |
| 管理员后台 | 邀请与账号、提交状态、依赖申请、执行节点、队列、正式排赛、结果发布 |

视觉方向延续城市的蓝紫色科幻风格，表单、代码说明和状态文字优先保证可读性。比赛与回放页面使用真实场景画面；提交页面保持简洁。当前交互预览用于确认流程，不接入真实账号、上传或仿真。

## 4. ZIP 格式

第一版建议固定入口，降低初学者配置成本：

```text
submission.zip
├── submission.json
├── policy.py
├── models/             # 使用模型时放离线权重
└── src/                # 可选辅助模块
```

允许压缩软件额外包一层目录，平台在静态检查时规范化；规范化后必须只有一套明确的根目录文件。文件名大小写按 Linux 环境处理。ZIP 内不包含虚拟环境、安装器或启动脚本。

`submission.json` 提议为：

```json
{
  "name": "我的搜索策略",
  "api_version": 1,
  "entry_point": "policy:Policy",
  "environment": "arena-python-v1",
  "description": "可选的版本说明"
}
```

`arena-python-v1` 是方案中的环境标识示例，实际可用名称和具体依赖以平台发布为准。初版固定 `policy:Policy`；平台生成 V001、V002 等提交编号，不依赖选手自己填写版本号。包内路径均相对提交根目录解析；选手不能指定服务器任意文件路径。

ZIP 大小、解压后大小、文件数和压缩率上限由管理员根据机器配置发布，页面在上传前显示。拒绝越界路径、符号链接、重复冲突路径、加密压缩包和异常膨胀压缩包。源码和模型不进入公开下载接口。

## 5. 代码接口

保持已有 [INTERFACE.md](INTERFACE.md) 的行为约定，网页提供便于初学者阅读的同源说明。

```python
class Policy:
    def __init__(self, player_id=0, config=None):
        self.player_id = player_id

    def act(self, observation):
        return {
            "joint_targets": observation["proprio"]["q"].copy(),
            "fire": False,
        }
```

这段仅用于展示输入输出格式：复制当前关节角不构成稳定站立或行走策略，也不作为正式比赛基线。

| 输入 / 输出 | 约定 |
| --- | --- |
| 入口 | `Policy(player_id=0, config=None)`，每次调用 `act(observation)` |
| RGB | `visual.rgb`：uint8、H×W×3、RGB 顺序 |
| 深度 | `visual.depth`：H×W 浮点数，单位米，沿相机光轴的深度 |
| 本体状态 | `proprio` 中的关节顺序、角度、角速度、姿态、角速度和脚部接触指示 |
| 任务与自身状态 | `tasks` 为公共及自己的任务；`game` 为自己的分数、生命值和冷却等 |
| 复位 | `reset_count` 变化时策略自行重置运控历史 |
| 关节输出 | `joint_targets`：按 `joint_names` 顺序给出 29 个有限实数，单位 rad |
| 开火输出 | `fire`：布尔值；实际开火仍受裁判的生命、冷却和禁火规则约束 |
| 更新频率 | 当前控制周期 0.02 秒、图像周期 0.10 秒；图像允许重复帧 |

慢速视觉模型应缓存识别结果，让运动控制继续返回动作；图像采样时间可用于判断是否有新帧。平台不提供隐藏物体坐标、对方私人任务或直接导航目标；保留现有公平观测边界。

当前本地原型初始化超时、推理超时和异常的具体行为以现有文档与配置为准。多人平台应发布独立、带版本的运行限额；不在此方案中擅自修改比赛判罚、计分或异常判负规则。

## 6. 检查与报错

状态依次为：已保存 → 静态检查 → 等待运行检查 → 隔离运行检查 → 接口通过 / 检查失败。执行节点未就绪时停在等待状态，并解释原因，不能退回到宿主机直接导入选手代码。

| 错误示例 | 给选手的提示 |
| --- | --- |
| 根目录缺少 `policy.py` | 列出期望目录结构，并提示是否多包了一层目录 |
| 清单无效 | 指出 JSON 行列或字段、实际值及可用环境版本 |
| 找不到 `Policy` | 指向 `policy.py`，显示期望类名和方法签名 |
| 模型路径错误 | 显示包内相对路径，提示将权重放入 `models/` 并随 ZIP 上传 |
| 依赖不存在 | 显示缺失库及环境版本，提供申请管理员添加依赖的入口 |
| 动作长度 28 | 显示“要求 29 个关节，实际 28 个”，链接关节顺序说明 |
| NaN / 非布尔开火 | 指出动作字段及问题；不生成该周期射击 |
| 初始化 / 推理超时 | 显示触发的已发布限额和建议；详细日志仅本人及管理员可见 |

静态检查不执行导入，不证明代码安全；运行检查只验证能否按接口运行，不保证竞争能力。错误提交可修复后上传新版本，历史记录不被覆盖。

## 7. 统一环境与执行边界

统一环境公开 Python、MuJoCo、数值库、模型推理框架、GPU 支持情况及版本。第一版不接受选手任意安装依赖或执行自定义安装脚本。管理员批准额外依赖后发布新环境版本，原提交继续绑定旧版本，避免复现漂移。

当前代码只具备受信本地 Python 进程运行方式，不是陌生代码的安全执行服务。上线多人运行前需要：

- 选手策略与仿真、裁判、网站分离，容器或等效隔离实例中执行；提交只读、私有临时目录、禁外网、限制进程和资源。
- 仿真只发送公开观测、接收严格校验的动作。跨执行边界采用受限消息结构与数组格式，不能延用可执行反序列化的 Python pickle 作为陌生代码边界。
- 不把裁判内部状态、隐藏场景文件、其他选手提交或服务器凭据挂载给策略。运行权限与实际可读文件都要验证。
- 明确 CPU、内存、磁盘、初始化时长、单步响应和总时长限额；GPU 节点另做支持探测与资源分配。
- 执行节点不可用时，平台允许保存与静态检查，但停止导入、练习和正式运行，并向管理员提示处理办法。

本机检查时发现 Docker 命令可用，但 Docker Linux 引擎未连接；因此不能把“已装 Docker”写成隔离能力已就绪。本机可见 AMD 集显，另有设备规格尚未提供；不能承诺当前机器支持 CUDA 或多人 GPU 推理。部署时探测真实节点能力，并据此发布环境版本。

## 8. 排队、正式比赛与复现

- 第一版同时运行一局，两名选手策略分别运行；多人的上传和静态检查可继续处理。
- 正式比赛在下一局开始时优先，默认不打断已经开始的练习。管理员可以暂停接收新练习；每人排队和活动练习上限由平台发布。
- 练习默认让选定的同一版本以两个独立实例对局，分别获得自己的机器人观测；主测视角默认 player 0。也可选择自己另一个通过检查的历史版本对战。这样第一次提交就能练习，不需要读取他人的私有策略。是否提供练习专用固定对手后续单列，不把内部演示运控变为正式比赛默认基线。
- 管理员安排正式对局，绑定双方提交摘要、环境版本、机器人版本、场景和裁判配置。相同场景随机条件对双方公平；隐藏种子由裁判保管。
- 正式发布只包含成绩、允许公开的事件及回放。官方重跑由管理员管理，并保存原因及新记录，不覆盖原始结果。
- 复现清单保存提交摘要、环境镜像摘要、平台和资产版本、裁判配置、随机种子及随机源设置、运行日志与轨迹。隐藏种子留在管理员侧；不能仅凭同一随机种子承诺不同硬件上的逐位确定性。

## 9. 实施顺序与验收

1. 确认本方案与交互预览；明确哪些按钮与信息对选手有用。
2. 实现账号、权限、ZIP 保存、不可覆盖版本和静态检查；不提前执行陌生提交。
3. 接入并验证隔离执行节点、接口检查、单局队列及现有 MuJoCo 裁判。
4. 打通练习、正式排赛、结果、权限受控的真实回放和复现记录。
5. 统一蓝紫色视觉、状态呈现、上传反馈和移动端布局。

上线验收包括：两个账号看不到对方私有文件和练习；重复上传产生新版本；压缩包无法写出提交目录；节点未就绪时无法执行代码；非法动作和异常只按发布规则处理；正式报名不会被新上传覆盖；正式回放中不泄露代码、凭据或私人日志。

首版已从交互预览推进到真实账号、上传、隔离检查、单局队列与回放。实现状态与验收证据见 [STATUS.md](STATUS.md)。
